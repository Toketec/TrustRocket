# TrustRocket 业务项目 — Agent 协作入口

## 核心契约

本项目只使用装备材料、技术支持、案例沉淀和一线运营四个一级业务域。TrustRocket 定义规则、结构、流程和交接语义，不是 CRM、工单系统、客户数据库、在线客服、知识库产品或 Agent 平台。

执行者可以是 Human、AI Agent、Script、Automation、External Service 或组合；更换执行者不改变 Goal、Trigger、Input、Preconditions、Procedure、Output、Acceptance、Exception、Escalation 与 Permission。高风险判断、审批和责任不得因自动化而消失。

## 读取顺序

1. 读取本文件。
2. 读取 `.trustrocket.json` 了解四域和素材来源。
3. 按当前任务只读目标业务域及必要的关联内容。
4. 需要完整标准时读取 TrustRocket 框架的 `trustrocket-convention.zh.md` 与 `SKILL.md`。

禁止为了“理解项目”无边界全量扫描；信息不足时再扩大读取范围。

## 任务路由

| 请求 | 主要业务域 | 必要闭环 |
|:--|:--|:--|
| 创建、改写、校验指南、SOP、FAQ、培训或验收材料 | 装备材料 | 检查案例与支持事实，输出一线反馈入口 |
| 受理、诊断、解决、升级或验证问题 | 技术支持 | 判断案例、装备、运营和产品反馈 |
| 检索、创建、合并或改进案例 | 案例沉淀 | 判断装备修正、支持引用和外部反馈 |
| 汇总客户、POC、交付、售后、风险或健康度 | 一线运营 | 路由技术、案例、装备或跨体系 Handoff |

混合请求按真实工作依赖顺序执行，避免在多个域复制同一事实。

## 执行契约

核心任务必须明确 Goal、Trigger、Input、Preconditions、Procedure、Output、Acceptance、Exception、Escalation 与 Permission。Human 与 Agent 可执行同一 Contract，但高风险判断、审批和责任不得因自动化而消失。

ToB 与 ToC 使用同一四域结构，不创建平行目录。差异通过场景、Policy、Workflow 和参数表达。

## 文件规则

- 四域内可以按业务需要创建普通目录。
- 任一普通目录直接包含业务 Markdown 时，必须同时在同级建立 `source/` 和 `cut/`；没有 Markdown 时默认不建立。
- 原始文件放入对应 Markdown 目录的 `source/`，切出资源放入同级 `cut/`。
- 基于文档创建的小程序或应用可以使用代码项目自身所需的目录结构，其内部 Markdown 不套用 `source/`、`cut/` 规则。
- 应用根目录可登记到 `.trustrocket.json` 的 `application_paths`；常见项目清单也可由 Validator 自动识别。
- 用户素材和切出资源使用 `user-` 前缀；公共素材不得使用该前缀冒充用户内容。
- 生成内容优先写入 Markdown。未经明确要求，不生成 DOCX、XLSX、PPTX、PDF 或图片包装。
- 截图优先保留原图；流程与关系只有在不遗漏、不误解、不编造时转为 Mermaid 或文本结构。
- 新增或移动素材时同步维护 `.trustrocket.json` 的 `materials`。

## Markdown 规则

- 业务文档只允许 `#`、`##`、`###`。
- 有子标题的标题不得直接有正文。
- 正文只写在当前分支叶子标题下。
- 装备材料使用最小充分信息，不堆砌背景、术语、重复总结或空泛内容。
- 不强制所有材料使用同一模板；结构由读者、场景和风险决定。

## 项目级 Skill 沉淀

- `skills/` 只保存用户已确认、可重复执行且效果稳定的流程。
- Agent 可在完成当前任务后建议沉淀，但未经用户明确确认不得创建、修改或提升为 Skill。
- 沉淀前必须把临时操作抽象为稳定的触发条件、输入、步骤、输出、验收和异常处理。
- 每个 Skill 位于 `skills/<skill-name>/`，必须包含 `SKILL.md`；可按需包含 `scripts/`、`references/`、`assets/`。
- 脚本必须参数化，不得硬编码本机路径、代理、Token、Cookie、密钥、客户敏感信息或单次任务输入。
- 一次性脚本、调试片段、未验证方案和仅对单个文件有效的过程不得进入 `skills/`。
- 项目级 Skill 是执行方法，不代替四域中的业务事实、原始材料或最终产物。

## 支持与知识闭环

技术支持先统一问题语义：问题、期望、实际、环境、影响、时间线、证据、已尝试动作、权限和安全。诊断区分事实、假设和未知；关闭前验证结果、反馈相关方并处理临时方案责任。

案例不是会议纪要。它必须可供下一位人员判断是否适用并执行，且包含不适用条件。重复经验优先合并到单一当前事实。

产品缺陷输出标准 Handoff 给 SpecRocket，不直接修改或依赖 SpecRocket 内部实现。

## 状态边界

一线运营可维护客户、项目、POC、交付、售后、SLA、风险、续费与健康度等外部业务状态。

禁止创建 `STATUS.md`、`PROGRESS.md`、`WORKLOG.md`、`TODO.md` 等 TrustRocket 自身状态文件，禁止写 AI scratchpad、维护任务追踪或“本轮完成/下次继续”。

## 权限与安全

Agent 可以搜索、分析、汇总、草拟、诊断和提出建议，并在授权范围执行低风险动作。下列动作必须停在审批点：

- 删除、覆盖、大规模移动或导致数据丢失；
- 生产环境高风险操作、核心配置和安全策略变化；
- 商业承诺、合同责任、重大客户沟通或事故定级；
- 高风险恢复与敏感信息扩大传播。

不把个人代理、本机用户目录、Token、Cookie、密钥、私有 DNS 或临时 workaround 写入项目规则、配置和可复用文档。

## Git 边界

默认只允许查看 Git 状态、差异与历史。未经使用者明确要求，不执行提交、推送、标签、合并、变基或发布。

## 完成条件

只在 Acceptance 满足且证据充分时宣称完成。无法完成时说明事实、缺口、风险、已尝试动作、最小下一步和需要的角色，不伪造验证结果。
